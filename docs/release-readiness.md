# Versions and release readiness

Public versions use `vX.Y.Z`. Python package metadata and the read API use `X.Y.Z`, without the display prefix. The current checked version is `v0.8.13`. Its maturity is **Experimental alpha**. The number is not a fraction of the work completed.

Earlier source declarations such as `0.8.0a1` remain in published history. They have not been renamed or retagged. No Git tags existed when this policy was reconciled on 2026-11-03. Minor numbers will not advance for each development checkpoint. Version selection follows the scope of an accepted change, with compatibility and maturity stated separately.

`v1.0.0` means the first complete, confident delivery of the recorded Monitoring vision. Passing a demo, adding an adapter or reaching a particular iteration count does not satisfy it. The release decision requires the following acceptance evidence.

| Feature set or boundary | Required for v1.0.0 | Current gap |
| --- | --- | --- |
| Local usage reconstruction | Supported producer versions, actual authorized source checks, replay/stream/resume/counter-reset behavior and cost provenance demonstrated end to end | One owned Claude Code 2.1.308 JSONL source has actual append/replay/API/UI proof. A historical Codex `0.162.0-alpha.17.2` file has actual parser/ledger/API/UI proof and exact cumulative-bucket comparison, but no fresh append. Claude's incremental follower has actual idle/restart and fictional rotation/truncation/partial-line checks. A later same-message token revision has an audited correction and ledger revision in fictional tests; the owned Claude file replays unchanged. Real changed-token behavior, current Codex following, provider-driven rotations, larger histories, source overlap and cost provenance need supported workflows. |
| Sessions, workers and chronology | Useful terminal/web inspection of real producer lifecycle, hierarchy, history and stale/unavailable evidence, with explicit coverage | One explicitly integrated owner process has live lifecycle qualification. Optional CodeBurn status output reports recent transcript writes, not process liveness. Opt-in macOS OS samples show process presence and resources separately, with unknown session/worker mappings. One private combined Claude/Codex dashboard workflow keeps old usage stale and process samples current. A fresh owned Claude file now supplies prompt, response-end and Stop-hook observations separately, but not generic session closure or process linkage. Broad local/connected runtime coverage remains incomplete. |
| Usage analysis | Practical provider/model/surface/project/date filters, graphs and reports, disjoint tokens, estimated/billed/unknown costs and dated currency conversion | The current reports cover a bounded ledger. Larger-history analysis, richer visual comparison and complete source coverage remain unqualified. |
| Quota, pace and budgets | Supported account windows, retained values, qualified forecasts and useful explicit budget thresholds without spending or reset authority | Codex quota and linear usage scenarios exist. Other provider collectors, budget thresholds and notifications remain incomplete. |
| Connected tracing | An authorized configured SDK/OpenTelemetry or remote export workflow with causal hierarchy, failures and overlap rules | General receivers, cloud collectors and distributed tracing remain planned. A normalized file contract alone is not that workflow. |
| Reliable private operation | Source selection/recovery, bounded diagnostics, retention/correction controls, useful capacity, accessibility and representative desktop/phone acceptance | A bounded Claude cursor and audited correction are implemented; durable cursors across restarts, retention and larger-ledger operation remain planned. Current bounds and synthetic checks do not establish production readiness. |
| Receiving integration | Accepted standalone-to-Deep journeys against exact owner pins, reconnect/failure behavior and representative live source evidence | Deep has its own Monitoring view. Every newer standalone feature has not been admitted there, and live session/UAT acceptance remains separate. |

The [feature catalog](featuresets.json) and [roadmap](roadmap.md) define the cohesive workflows. Existing work logs retain the detailed evidence. A v1.0.0 review must identify an accepted result for each row and disclose any deliberately excluded scope. It must not convert an untested feature into an implicit exception.
