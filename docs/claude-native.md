# Explicit Claude Code JSONL source

Choose one Claude Code JSONL file you own or are authorized to read. Monitoring does not discover home-directory sessions, read credentials, run Claude or install hooks. A selected file can be followed as it appends:

```sh
python3 -m monitoring_ai serve --db /path/to/private/events.sqlite \
  --file /path/to/selected/claude-session.jsonl --format claude \
  --source-id owned-claude --project my-project
```

The local server checks the selected file every two seconds. After its first scan, an in-memory cursor reads only newly completed lines. A trailing partial line is reread when more bytes arrive; its raw bytes are not retained between polls. The cursor advances only after the matching ledger batch commits. File replacement or truncation resets the cursor to the start of the new file, while accepted ledger history remains. Reopening Monitoring rescans the selected file and replays identical events. The selected file remains capped at 32 MiB and each file generation at 50,000 rows; the cursor is not persisted, and in-place edits to older lines in a growing file are not fully detected.

Each parsed native line is reduced before it joins the accumulated row list: assistant ID, model, four usage counters and structured tool-use IDs/names; user tool-result ID and error flag; source type, session ID and timestamp. Prompts, response text, tool arguments/results, working paths and unrelated metadata are not retained in that row list or emitted through the API. The bytes being read and each JSON object are transiently present in the local reader while parsing. The retained projection contains native session and message IDs in process memory; the ledger stores hashed session IDs.

The same source alias and project alias must be reused across restarts. A message ID supplies one usage event. Later copies with the same normalized usage but a different native row timestamp keep the **first accepted event timestamp** and add nothing, even when a rotated file contains only that later copy. This timestamp allowance applies only to Claude usage events under the explicit Claude follower; normalized producers retain exact immutable replay. Changed counters or model for an accepted message refuse the whole attempted batch and retain prior accepted history. Repairing the selected source retries it from the last committed cursor. There is no mutable correction protocol: one would need an auditable replacement and a new ledger revision that invalidates pinned report/history reads. An exact duplicate or incomplete trailing line does not advance the ledger revision. Completed structured tool-use/result pairs yield metadata-only tool records; incomplete pairs remain uncounted. A rotated copy of a tool result with a changed result timestamp still refuses, since tool chronology has no timestamp-only exception.

The four token buckets are input, cache read, cache write and output as reported by the native message. No cost is assigned unless an explicit dated price book separately covers the model; that is an estimate, not billed spend. Native usage rows carry no lifecycle status. A recent usage record, a followed file or a present CLI process does not prove a worker is running. The Sessions view therefore shows unknown lifecycle when no status evidence is supplied. Session totals may overlap completed CLI result summaries or another collector; do not import the same conversation through two routes under different aliases.

One actual task-owned Claude Code 2.1.308 project-only session was checked. Its first assistant message was followed into the ledger, and a resumed second message appended to the **same** native file while Monitoring was running. The API revision moved from one to two, with the first timestamp stable and no source read failure. Native per-message token buckets matched the two normalized usage events, and the private dashboard displayed the real session and usage without raw text, paths or tool arguments. Public tests use fictional records. Broader provider versions, advisor/sidechain accounting, provider-driven file rotation, larger histories, source overlap and corrections remain unqualified.

The incremental reader was also checked on that 205,043-byte owned file without exposing its contents: its initial normalized events matched the full parser, five idle cursor reads had a median 0.245 ms read/parse time, and a restart replay added zero events. The original first scan took 2.866 ms in that local measurement. A separate five-sample complete observer refresh, including ledger replay checks, had a 1.733 ms idle median; its first refresh took 5.297 ms. Fictional tests cover complete-line append, partial lines, replacement, truncation, timestamp-only replay, tool pairs across appends and atomic rejection of changed usage through the loopback API. These measurements and fixtures do not qualify provider-driven rotation, in-place rewriting or changed-token correction on real sessions.
