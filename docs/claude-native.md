# Explicit Claude Code JSONL source

Choose one Claude Code JSONL file you own or are authorized to read. Monitoring does not discover home-directory sessions, read credentials, run Claude or install hooks. A selected file can be followed as it appends:

```sh
python3 -m monitoring_ai serve --db /path/to/private/events.sqlite \
  --file /path/to/selected/claude-session.jsonl --format claude \
  --source-id owned-claude --project my-project
```

The local server checks the selected file every two seconds. After its first scan, an in-memory cursor reads only newly completed lines. A trailing partial line is reread when more bytes arrive; its raw bytes are not retained between polls. The cursor advances only after the matching ledger batch commits. File replacement or truncation resets the cursor to the start of the new file, while accepted ledger history remains. Reopening Monitoring rescans the selected file and replays identical events. The selected file remains capped at 32 MiB and each file generation at 50,000 rows; the cursor is not persisted, and in-place edits to older lines in a growing file are not fully detected.

Each parsed native line is reduced before it joins the accumulated row list: assistant ID, model, four usage counters and structured tool-use IDs/names; user tool-result ID and error flag; source type, session ID and timestamp. User rows also retain only whether the content shape indicates a prompt; assistant `end_turn` and system `stop_hook_summary` retain boolean markers. Native row UUIDs are hashed. Prompts, response text, tool arguments/results, working paths and unrelated metadata are not retained in that row list or emitted through the API. The bytes being read and each JSON object are transiently present in the local reader while parsing. The retained projection contains native session and message IDs in process memory; the ledger stores hashed session IDs.

For an explicitly selected Claude source, snapshot and report include optional `claude_responses: monitoring.claude-responses.v1`. It gives at most 100 latest prompt-to-response spans with hashed session, source/project aliases, UTC prompt time, optional first distinct assistant `end_turn` time, optional `stop_hook_summary` time and the strongest observed marker. A new prompt starts a new span even if the previous prompt lacks an end marker. Repeated assistant message IDs do not move the first end time. Source failure retains prior spans but marks their source unavailable; a paused or disconnected browser treats all rows as history. These native observations do not enter the event ledger, advance its revision, imply current activity or close a CLI session. A Stop hook record means hook processing was recorded, not that every failure, interrupt or session exit was observed. [Claude's hook reference](https://code.claude.com/docs/en/hooks) distinguishes Stop from StopFailure and does not define either as a session-close receipt. The panel applies source, project and exact session filters; other event filters do not apply.

The same source alias and project alias must be reused across restarts. A message ID supplies one usage event. Identical later copies keep the **first accepted event timestamp** and do not change usage, even after rotation. The follower sends every complete source version in file order to the ledger. A strictly later native row for the same stable message may revise its four token counts. The current event keeps its first timestamp, its tokens are replaced atomically, and a private SQLite correction row preserves the prior and next normalized payloads, source record time, observation time and new ledger revision. Existing report/history pages pinned to the old revision must restart. Accepted earlier versions replay after restart without reversing the correction. A different version at an already recorded timestamp, an unrecognized older timestamp, changed model/identity or changed tool chronology refuses the whole attempted batch. The cursor stays at its last commit for a repaired read. Normalized producers retain exact immutable replay.

The correction audit contains normalized metadata and token counts, never prompt or tool text. `replayed` in the input read status counts accepted existing identities, including corrections; `added` counts new event identities. A single `--file` source status also reports `corrected` for its latest read. The multi-input `monitoring.inputs.v1` shape and Deep's existing strict consumer contract remain unchanged. A rotated copy of a tool result with a changed result timestamp still refuses.

The four token buckets are input, cache read, cache write and output as reported by the native message. No cost is assigned unless an explicit dated price book separately covers the model; that is an estimate, not billed spend. Native usage rows carry no lifecycle status. A recent usage record, a followed file or a present CLI process does not prove a worker is running. The Sessions view therefore shows unknown lifecycle when no status evidence is supplied. Session totals may overlap completed CLI result summaries or another collector; do not import the same conversation through two routes under different aliases.

One actual task-owned Claude Code 2.1.308 project-only session was checked. Its first assistant message was followed into the ledger, and a resumed second message appended to the **same** native file while Monitoring was running. The API revision moved from one to two, with the first timestamp stable and no source read failure. Native per-message token buckets matched the two normalized usage events, and the private dashboard displayed the real session and usage without raw text, paths or tool arguments. Public tests use fictional records. Broader provider versions, advisor/sidechain accounting, provider-driven file rotation, larger histories and source overlap remain unqualified.

The incremental reader was checked on that 205,043-byte owned file without exposing its contents: its initial normalized events matched the full parser, five idle cursor reads had a median 0.245 ms read/parse time, and a restart replay added zero events. The original first scan took 2.866 ms in that local measurement. A separate five-sample complete observer refresh, including ledger replay checks, had a 1.733 ms idle median; its first refresh took 5.297 ms. A private copy of the older ledger replayed the actual source into the new correction schema with the same two events and revision 2, four recorded native row versions and zero corrections. That first scan and replay took 4.092 ms; five idle read/replays had a 1.563 ms median. Fictional tests cover later-token correction, audit rows, old-version replay, partial lines, replacement, truncation, ambiguous-version rollback and loopback revision invalidation. No changed-token row was observed in the actual owned file. These measurements do not qualify provider-driven rotation, in-place rewriting or correction behavior across broader real sessions.
