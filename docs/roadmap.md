# Product roadmap

The goal is one useful view of local and explicitly connected AI activity, independently usable and consumable by Deep AI. Feature depth will grow through demonstrated user journeys.

| Stage | Scope | State |
| --- | --- | --- |
| Local foundation | Metadata ledger, hierarchy, chronology, tokens/costs, web/terminal views, filters, native file imports, read contract | Implemented alpha. Synthetic and fixture qualification. |
| Reliable daily use | Incremental cursors, source health details, correction protocol, retention controls, configurable evidence windows, deeper session drill-down and larger ledgers | Explicit multi-file configuration, independent read health, retained-history recovery, setup checks, disposable ingestion previews, capability-versus-observed coverage and scoped entity-history pages implemented. An explicit Claude cursor and audited same-message token corrections are implemented; persistent large-history cursors, real changed-token qualification and retention remain planned. |
| Connected sources | Reviewed adapters for more coding tools, supported OpenTelemetry ingestion and authorized cloud exports | Planned. No new credentials or hooks installed. |
| Quota and budgets | Independently sourced provider quota windows, reset times and budget notifications, with cost provenance preserved | Codex native allowance read, normalized quota imports and an optional on-screen observed UTC-day token threshold implemented. Other collectors, cost budgets and notifications planned. No quota-to-dollar inference. |
| Rich analysis | Period reports, tool categories, timing, comparisons, exports and transparent forecasts | Source freshness, qualified linear scenarios, period comparisons, project/model/day reports, explicit tool categories and recorded-duration statistics implemented. Workflow-quality metrics and richer visual analysis need new supported evidence. |
| Shared appearance | Portable semantic palettes, system choice and validated local overrides | Shared package adopted with Monitoring controls and storage. Shared primary/contextual navigation geometry is adapted with independent layout preferences. Representative dashboard qualification accompanies each release. No automatic cross-application settings sync. |
| Deep integration | Reviewed same-origin bridge and unified monitoring view beside existing owner activity | Consumer adapter supplied. Deep source 95cbcdc mounts snapshot/reconnect views with synthetic checks. Detailed-report and managed-input additions await consumer adoption; live telemetry and UAT promotion remain unqualified. |

Public demos remain synthetic. A capability is implemented when its complete input-to-consumer journey works and its meaningful failure behavior is checked. Live personal-source qualification, user acceptance and production readiness remain separate evidence.

The [v1.0.0 acceptance requirements](release-readiness.md) govern release readiness separately from version numbers. Completed Claude CLI result capture adds a narrower authorized source with cumulative model-level accounting. It does not qualify interactive transcripts, general lifecycle discovery or cloud tracing.

Runtime-owned normalized emission and the parent-first Sessions view are qualified against one actual owned CLI review process. Source health responses now derive their aggregate status from the included inventory. General session discovery, continuous large-source retention and provider-internal lifecycle remain unqualified.

An explicitly selected CodeBurn v74 daily cache now supplies a separate replaceable daily view. It cannot establish session lifecycle, call chronology or a complete billing basis. Native per-call cache reconciliation and broader provider compatibility remain separate work.

An explicitly selected existing CodeBurn menubar status output can provide recent transcript-write observations with independent source-generation age. This optional compatibility adapter does not identify running processes or replace native provider collectors. A fresh source with represented sessions still needs actual qualification.

An owned Claude Code 2.1.308 JSONL source is qualified end to end for a fresh append: source message, metadata-only projection, normalized tokens, ledger replay, API revision and private dashboard. The explicit follower reads only complete appended lines after its first scan. A strictly later same-message token revision now has an auditable atomic replacement and new read revision; ambiguous versions refuse. Actual owned-source migration/replay kept two events and revision 2 with no observed correction; fictional correction/rotation/partial-line checks pass. This does not establish general directory discovery or lifecycle inference. Persistent large-history cursors, provider-driven rotation and wider real changed-usage qualification remain next source gaps.

A historical Codex `0.162.0-alpha.17.2` JSONL file now qualifies a second native source through projected parsing, 126 cumulative usage deltas, ledger replay, loopback API and private dashboard. Its input/cache-read/output sums matched the final source counters. Separate per-response records did not sum to those cumulative totals and remain excluded. The installed CLI inventory's `0.160.0` does not label this file. A fresh Codex append, incremental cursor, nonzero cache-write interpretation, broader source versions and lifecycle proof remain open.

An opt-in macOS OS-process sampler now supplies fresh PID/parent PID, executable basename, CPU, RSS and start-time observations independently of session records. A task-owned process appeared and then disappeared across real samples; matching AI executables appeared across repeated private samples. Process-to-session mapping and cloud activity remain unknown.

The v0.8.11 dashboard puts opt-in local OS process observations on Overview above usage charts, with a link to the separate Sessions process table. A private actual-source qualification combined one selected Claude file and one historical Codex file in the same ledger: both read successfully, project filters selected their own events, old usage remained stale, process samples updated independently, costs remained unknown and no process was mapped to either session. The finite qualification owner stopped after capture. The default OS sample cadence is five seconds, configurable from two to 60 seconds; this reduces polling duty without changing the two-second browser and event-source refresh. General live session linkage is still open.

The v0.8.12 native Claude response panel separates prompt, model `end_turn` and Stop hook markers from ledger lifecycle. One actual selected owned source now has four response spans: two earlier Stop hook observations, one failed prompt with no end marker, and one later successful response end without a Stop hook marker under safe mode. Repeated assistant rows do not create extra spans. The successful CLI result/exit is a separate task receipt, not a generic native session-close event. Initial selected-file scan and immediate replay were measured locally; public checks use fictional rows. Unknown activity and absent process-to-session linkage remain explicit. Fresh Codex append, robust general session termination, authoritative process relation and wider provider lifecycle remain open.

A further owned Claude append was observed while a finite v0.8.12 Monitoring owner polled the selected file. Its prompt and response end became a fifth native span and reached the loopback API. At a two-second owner polling interval and 0.2-second measurement probe, first projected-row observation to first API observation was 1.284 seconds for the prompt and 1.498 seconds for the response end. This is a sampled local projection-to-API delay, not provider write syscall-to-browser paint. The project-only Claude review identified that out-of-order markers could attach to a later prompt. v0.8.13 requires forward temporal order, refuses a response after Stop, handles malformed optional rows defensively, and keeps the previous session-closure and process-link limits. Public tests cover these edge cases with fictional rows.

The v0.8.14 Codex follower now shares the bounded complete-line cursor with Claude but keeps Codex cumulative accounting and stricter replacement semantics. On the unchanged, previously authorized historical Codex source, it matched the full parser's 126 usage deltas, accepted them once, then added zero on idle and restart replay. The finite API exposed 126 calls, unknown lifecycle and no Claude-response block. Five idle source reads had a 0.207 ms median versus a 36.418 ms first scan in one local run. Fictional append, partial-line, full-prefix replacement, refused partial replacement and recovery checks pass. The selected file had not changed since November 2; no fresh task-owned Codex log was found within this workspace. Current Codex producer append, segmented rotation and general provider lifecycle remain unqualified.

The v0.8.15 correction preserves externally supplied programmatic source loaders; only validated manifest `Source` entries use the native file cursor. Hosted v0.8.14 Python checks exposed the distinction through older programmatic-source coverage fixtures. No native producer field or external read contract changed.

The v0.8.16 source setup flow adds one explicitly selected file to a new private manifest without hand-editing JSON or replacing the prior manifest. On the two previously authorized local files, CLI create → add → check → preview accepted Claude and historical Codex independently, proposed five and 126 additions in a disposable ledger, and a finite owner showed 131 usage records with both inputs following and all costs unknown. The output manifests were 0600 and no source path entered the API. The Codex file remained historical; source setup did not discover new sessions or establish live worker state.

The v0.8.17 guided terminal setup makes that selection workflow visible from Settings and a single `setup` command. It asks for one explicit file, format and safe aliases, creates a new private selection, checks supplied evidence, and prints preview/restart commands. On the two previously authorized sources, the wizard created two 0600 selections and a disposable preview proposed five Claude and 126 historical Codex usage records; neither file supplied lifecycle status. The running owner and Deep read contract were unchanged. A fresh Codex producer append remains unavailable under the existing source-access boundary.

The v0.8.18 optional UTC-day token threshold evaluates all accepted usage independently of dashboard filters. It excludes cumulative Claude CLI result summaries because their capture time is not work time, and excludes future-dated records until their timestamps arrive. Usage & costs and the terminal show observed progress, while Settings owns configuration guidance. This is on-screen only; unconnected sources remain unknown, and it neither enforces a provider limit nor interprets billing. Cost budgets and outbound notifications remain planned.

The v0.8.19 Report download saves the exact displayed aggregate response as local JSON, with its observation time, ledger revision, normalized filters and cost/coverage qualifiers. It is disabled when filters no longer match the displayed response; a retained report remains downloadable under its original filters with no freshness claim. The saved file has no raw event rows or transcripts. The standalone CLI already exposes the same report schema through `report --json`; the Deep receiving contract is unchanged. This improves inspection and personal export but does not add a cloud connector, complete account coverage or billed-cost evidence.

The v0.8.20 Codex turn panel reads only `task_started` and `task_complete` marker types from an explicitly selected native Codex file. Its projection hashes turn identities, retains marker timestamps and bounded source-reported duration/first-token measures, and discards message text, arguments and native IDs. The optional `codex_turns` response is separate from normalized usage and session lifecycle. A selected historical `0.162.0-alpha.17.2` file supplied nine paired marker groups, 126 usage deltas and zero active entities; real idle replay added zero usage. Initial and idle selected-file reads took 47.862 and 7.929 milliseconds in one local measurement. A private browser and strict consumer read showed all nine. This is historical turn chronology, not a fresh Codex producer append, running worker, successful task or session-close proof. Wider Codex versions and live source qualification remain open.

The v0.8.21 selected Codex source now also projects completed command, MCP and file-change item metadata into the existing tool ledger and Report, with source-limited outcome interpretation. Commands, arguments, results and paths are discarded before storage. The same historical file yielded 213 tool records alongside 126 usage deltas; first acceptance added 339, replay added zero. A finite two-source owner and private dashboard showed tool groups, source freshness and zero inferred active entities. This increases useful historical activity coverage but does not establish fresh Codex appends, live workers, billed costs or general producer compatibility. Unknown MCP/file-change outcomes remain explicit.

The v0.8.22 Report adds a bounded daily tool-category chart across the existing selected event filters. It uses UTC dates and explicit category/outcome counts, retains overall totals when the latest-100-date chart truncates and leaves missing dates unfilled. The previously selected historical Codex file supplied four tool dates whose counts reconcile to all 213 tool observations, 16 errors and 26 unknown outcomes. Five local report builds on the combined selected-source ledger had a 3.214 ms median. The chart improves historical analysis; it does not add live process or worker evidence. The selected Codex file did not contain an authoritative agent-spawn or worker-lifecycle item.
