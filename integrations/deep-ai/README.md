# Deep AI consumer

`client.ts` is a server-side, dependency-free TypeScript consumption adapter. It is delivered here for the Deep implementation owner to review and apply. This repository does not modify or claim deployment into Deep.

```ts
import { monitoringOwner } from "./client";

// Operator configuration on the Deep host, never a browser-supplied URL
const monitoring = monitoringOwner("http://127.0.0.1:5274");
const snapshot = await monitoring.snapshot({ project: "orbit-api" });
```

Deep should expose a same-origin read bridge to its browser. Use capabilities to check compatibility before showing a connected state. Poll snapshots every two seconds, stop polling when the view is closed, and retain last observations with a visible unavailable label on failure. Reconnect explicitly after the owner identity changes. No mutation, cancellation, execution or session reopening endpoint exists in this adapter.

Render `reported_state`, `state`, `stale`, `status_at` and `source_status` with their distinct meanings. A successful HTTP read does not refresh worker evidence. Cost amounts cover the indicated event count. Keep estimated, billed, unknown and unconverted subsets visible. Show the owner's supplied currency and FX provenance.

Owners from 0.2.0a1 add optional `monitoring.insights.v1` data to snapshot v1. It includes source age, selected-window pace, qualified linear forecasts and independent account-wide quota windows. Existing snapshot consumers remain compatible. Check the sub-schema before using it and handle absence. Quota percentages never establish project usage, worker activity, task authority or a dollar balance. Show quota `read_status`, capture age and reset-passed state separately. The API contract remains read-only. This repository supplies the updated consumer without changing Deep's checkout or running deployment.

Owners from 0.3.0a1 advertise `/api/v1/report` through capabilities. `monitoring.report(filters)` reads it and shares the same pinned process identity as snapshot reads. A restarted report owner cannot silently replace a bound snapshot owner. Earlier snapshot-only owners remain compatible with snapshot consumers and report reads fail unavailable rather than substituting data. The report schema keeps date bounds, previous-period qualification, cost coverage and unsupported measures explicit. This is a consumption handoff, not a duplicate Deep UI.

Deep's existing Signals activity, Maestro managed runs and native Codex session roster retain their own authoritative controls and exact IDs. Monitoring's source/session/entity tuple identifies an observation, not a command target. Do not route cancellation or opening actions from a monitoring row without an independently verified owner mapping. Do not add provider totals together when their underlying usage overlaps. See [the owner contract](../../docs/contract.md).

Owners from 0.4.0a1 advertise additive `monitoring.inputs.v1` inventory on configured snapshot/report responses. The supplied reader validates it when present and still accepts older owners. Show aliases, per-input outcomes and retained history separately from worker state. Input IDs are managed file aliases and may differ from event-source filters. No file paths or source-selection editor belong in the browser. Aggregate `source_status` keeps its existing states; `degraded` qualifies partial success. These additions are supplied for owner review; this task does not edit Deep.

Owners from 0.6.0a1 add optional `source_coverage` for managed inputs. It distinguishes adapter capability from actually supplied unique records, sample time from event age, and retained coverage from current readability. This inventory is global rather than usage-filtered, and can overlap across inputs. Never infer live workers from native usage files or sum these per-input counters as total activity. The normalized ingestion and existing input-health schema remain unchanged.

Owners from 0.8.0a1 advertise `event_filters` separately. `/api/v1/events` accepts an exact `entity` only with its `source` and `session`. This optional route extension enables entity history beyond the latest 100 snapshot events without changing snapshot/report filters or the supplied snapshot/report reader. A Deep history consumer should check the capability, preserve the snapshot's process identity, and pass the first event page's `revision` as `expected_revision` on every later page. Keep loaded pages separate from current snapshots and require an explicit restart after HTTP 409 or an owner identity change. Never silently combine revisions or fall back to an unscoped worker-name query. This repository's standalone history view does not imply adoption in Deep.

From `v0.8.1`, the supplied reader admits `claude-results` inputs with cumulative-result usage and unsupported lifecycle/tools. Older owners remain compatible. Show these observations as completed result summaries, with client-side estimates and declared receipt times. They are excluded from pace/forecast inputs and counted by optional `pace.excluded_summary_records`. Snapshot/report coverage adds optional `receipt_time_summary_records` so receipt-date totals can be qualified without implying actual call dates. These are read-contract additions for A's review, with no shared Deep edits or automatic source connection.

From `v0.8.25`, an owner explicitly configured with `otlp-jsonl` can return completed inference, agent-invocation and tool-span evidence. The supplied strict client accepts its `completed-inference-spans` / `completed-agent-spans-only` / `completed-tool-spans` capability tuple; older owners stay compatible. This is a file import with fictional qualification, not a network receiver or live remote worker feed. A must update its pinned client before upgrading a Deep owner configured with this format. See [the OTLP file contract](../../docs/otlp-jsonl.md).

From `v0.8.26`, an owner started with `--processes` may include the latest 60 aggregate successful OS samples in the optional `os_processes.history` block. A may ignore the field; the normalized event and strict snapshot/report client contracts are unchanged. This is local process resource history with gap markers, not an agent/session timeline or a remote worker feed. See [the OS process contract](../../docs/os-processes.md).

From `v0.8.27`, the standalone Overview presents a source-type coverage comparison when a recent OS Claude/Codex executable sample and managed native input coverage coexist. It consumes existing optional blocks and adds no read-contract field. Deep may adopt the presentation independently; its managed owner was not changed. The comparison never links a process to a file, session or worker.

The local candidate also advertises optional `/api/v1/sessions` for exact recorded-session selection beyond the snapshot's 500-entity bound. It is a separately paged, metadata-only index with shared non-state filters, alias-fragment search and revision-pinned later pages. A consumer can ignore it and retain existing compatibility. Adopting it requires owner discovery, identity/revision checks and honest recorded-history labels; it does not upgrade Deep's current session picker. See the [catalog contract](../../docs/contract.md#recorded-session-catalog).

The source updates reached the component and it naturally changed to current-status-unknown after the last capture aged out. No managed owner was upgraded or persistent bridge installed.
